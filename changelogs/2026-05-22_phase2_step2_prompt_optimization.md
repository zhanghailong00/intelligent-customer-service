## 设计决策

### 为什么用少样本而不是零样本？

| 方式 | 优点 | 缺点 |
|------|------|------|
| 零样本 | Prompt 短，延迟低 | 输出格式不稳定，边界 case 容易误判 |
| **少样本（采用）** | 分类更稳定，边界 case 处理更好 | Prompt 稍长（可接受） |

给 3-4 个典型示例后，LLM 能更好地理解分类边界。

### 为什么只给故障 Agent 加思维链？

| Agent | 是否需要 CoT | 原因 |
|-------|-------------|------|
| 产品 Agent | 不需要 | 信息查询类，直接返回结果 |
| **故障 Agent** | **需要** | 需要"分析现象 → 可能原因 → 排查步骤"的推理过程 |
| 培训 Agent | 不需要 | 资料推荐类，直接返回结果 |

思维链会增加延迟，只在需要推理的场景使用。

### 为什么要有拒绝策略？

没有拒绝策略时，LLM 可能编造不存在的产品参数或解决方案。明确的拒绝策略让系统在知识库没有相关内容时诚实告知，减少幻觉。

## 改动详情

### 1. 意图分类器 Prompt（少样本提示）

**改动前**：零样本，只给类别定义和示例
**改动后**：少样本，给 12 个分类示例 + 边界判断规则

**新增边界判断规则**：
- 涉及"实验/课件/教学/培训" → training
- 涉及"故障/报错/不亮/坏了/连不上" → fault
- 涉及"功能/参数/怎么用/规格/支持" → product
- 与实训设备完全无关 → confidence < 0.5

### 2. Agent System Prompt 优化

**三个 Agent 共同优化**：
- **角色扮演强化**：从"你是..."改为"你是'智科云联'实训设备的XXX，拥有丰富的XXX经验"
- **少样本提示**：每个 Agent 增加 1 个理想回答示例
- **拒绝策略**：明确什么时候说"我不确定"，减少幻觉

**故障 Agent 额外优化（思维链）**：
```
回答思路（思维链）：
1. 分析现象：用户描述的故障现象是什么？
2. 可能原因：根据参考资料，可能的原因有哪些？
3. 排查步骤：从最简单、最常见的原因开始排查
4. 解决方案：给出具体的操作步骤
5. 升级建议：如果以上步骤无法解决，建议联系技术支持
```

### 3. Agent 身份标签显示

**web/app.py** 回答末尾格式：
- 有 Agent 时：`[产品专家 | 意图：产品咨询，置信度：95%]`
- 打招呼/未知意图时：`[意图：打招呼，置信度：95%]`

## 面试亮点

1. **少样本提示（Few-shot）**：通过示例引导 LLM 输出更稳定
2. **思维链（CoT）**：故障排查时引导分步推理，提高诊断准确性
3. **拒绝策略**：明确何时说"我不确定"，减少幻觉，提高可信度
4. **角色扮演**：强化 Agent 角色定位，回答更专业、更有针对性
