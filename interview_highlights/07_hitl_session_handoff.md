# 面试亮点：HITL 会话快照 + 人工接管模式

---

## 一、问题背景

### 1.1 原始 HITL 流程

```
用户说"转人工" → 系统显示"正在转接" → 人工客服接手
```

**问题**：
1. 人工客服接手时是"空白状态"，不知道用户之前聊了什么
2. 人工回复后，系统又把后续消息交给 AI，形成死循环

### 1.2 目标

1. **无缝接力**：人工接手瞬间看到完整上下文和处理建议
2. **完整接管**：人工接管后所有问题都由人工处理，直到说"关闭"才恢复 AI

---

## 二、方案设计

### 2.1 会话快照（Session Snapshot）

HITL 触发时，从 State 读取数据 → LLM 生成结构化快照：

```python
{
    "core_need": "用户温湿度传感器指示灯不亮，需要排查故障",
    "hitl_reason": "Agent 拒绝回答",
    "suggested_plan": "1. 确认接线 2. 检查供电 3. 远程协助",
    "history": "用户：传感器不亮了\nAI：抱歉没有找到..."
}
```

### 2.2 快照数据流程

```
State（answer/messages/sources/confidence）
    ↓ 从 State 读取原始数据
LLM（DeepSeek）分析对话
    ↓ 生成核心诉求 + 建议方案
快照展示在前端
```

**关键点**：快照不是凭空产生的，而是基于 State 中已有的数据（Agent 回答、对话历史、参考来源）由 LLM 提炼而成。

### 2.3 人工接管模式

```
用户提问 → HITL 触发 → 显示快照
    ↓
人工回复 → "[人工客服] xxx"（所有后续消息走人工）
人工回复 → "[人工客服] xxx"
人工说"关闭" → 退出人工模式，恢复 AI
```

**为什么这样设计**：
- 真实客服场景中，人工接管后应该持续处理，不是回复一次就交回 AI
- "关闭"作为明确的退出信号，避免误操作

### 2.4 字段设计原则

**从人工客服的实际工作流程出发**：

| 字段 | 为什么需要 | 去掉了什么 |
|------|-----------|-----------|
| 核心诉求 | 5 秒了解用户要解决什么 | ~~对话摘要~~（与诉求重复） |
| 转人工原因 | 知道为什么转给我 | ~~情绪判断~~（人工自己能感受到） |
| 建议方案 | 知道下一步该做什么 | ~~优先级~~（没有排队系统就没意义） |
| 对话历史 | 需要时查看细节 | ~~设备识别~~（对话里一般会提到） |

## 三、技术实现

### 3.1 模块设计

```
app/hitl/
├── detector.py    # HITL 检测（前置+后置）
├── handoff.py     # 会话快照生成（新增）
```

### 3.2 生成流程

```
graph.invoke() 返回 State
    ↓
从 State 读取：answer, messages, sources, confidence
    ↓
generate_snapshot() 调用 LLM 分析
    ↓
格式化快照 → 展示在前端
    ↓
_hitl_active = True（进入人工接管模式）
    ↓
后续消息 → 显示为"[人工客服] xxx"
    ↓
人工输入"关闭" → _hitl_active = False（恢复 AI）
```

### 3.3 LangGraph interrupt 的坑

`interrupt()` 暂停图执行时，**不抛异常**，节点返回值**不合并到 State**。所以：
- HITL 检测在前端层进行（检查 Agent 回答中的拒绝关键词）
- 快照生成也在前端层进行（从 State 读取数据后调用 LLM）

### 3.4 降级机制

```python
try:
    snapshot = generate_snapshot(...)
except:
    snapshot = {"core_need": "...", "hitl_reason": "...", "suggested_plan": "请查看对话历史"}
```

## 四、面试话术

### 4.1 项目描述

> "HITL 机制有两个关键问题：人工接手时的上下文断裂，以及接管后的持续服务。我设计了会话快照机制，从 State 读取数据由 LLM 生成结构化快照；同时实现了人工接管模式，人工处理所有后续问题直到说'关闭'才恢复 AI。"

### 4.2 技术细节

> "快照的数据来自 LangGraph State——Agent 的回答、对话历史、参考来源。LLM 基于这些数据提炼出核心诉求和建议方案。这里遇到一个坑：LangGraph 的 interrupt 机制在图暂停时不更新 State，所以 HITL 检测和快照生成都移到了前端层。"

### 4.3 延伸讨论

| 面试官可能问 | 可以聊的方向 |
|-------------|-------------|
| 建议方案准不准？ | 基于 State 中已有的 Agent 回答和检索文档生成，质量取决于知识库覆盖度 |
| 为什么不用 Agent 生成快照？ | 快照生成是一次性调用，不需要工具调用和迭代，用函数更简单 |
| 生产环境怎么做？ | 接入企业微信/钉钉，快照推送到客服群 |
| 多轮对话怎么处理？ | State messages 自动包含完整上下文 |

---

## 五、一句话总结

> "从 State 读取数据，LLM 生成会话快照，人工接管后持续服务直到说'关闭'——完整的 HITL 无缝接力方案。"
