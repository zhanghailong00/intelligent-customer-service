# 面试亮点：HITL 双层检测架构（从 Bug 到架构重构）

---

## 一、问题背景

### 1.1 业务场景

智能客服系统需要支持 HITL（Human-in-the-Loop）机制，当 AI 无法处理时自动转人工。

### 1.2 原始架构

```
用户消息 → classifier_node（LLM 意图分类）→ Agent → hitl_checker_node（后置检测）→ END
```

HITL 检测仅在 Agent 执行完后进行（后置检测）。

### 1.3 发现的 Bug

用户说"转人工"时，系统返回"抱歉，您的问题似乎与实训设备无关"。

**根因**：LLM 将"转人工"分类为 `intent=unknown`（30% 置信度），走了 `unknown_node → END` 路径，**跳过了 hitl_checker_node**。

```
"转人工" → LLM 分类 → unknown（30%）→ unknown_node → END
                                                    ↑
                                          hitl_checker 从未执行
```

---

## 二、架构分析

### 2.1 为什么会出现这个 Bug？

| 问题 | 原因 |
|------|------|
| HITL 检测位置错误 | 仅在 Agent 节点后执行（后置），但 unknown 路径不经过 Agent |
| 系统控制意图被业务分类器吞掉 | "转人工"不是业务意图，但 LLM 无法区分系统控制意图和业务意图 |
| 逐个打补丁不可持续 | 每发现一个边界情况（投诉、退款...）就加特殊检测，代码越来越臃肿 |

### 2.2 核心洞察

**系统控制意图 ≠ 业务意图**

| 类型 | 示例 | 特点 | 处理方式 |
|------|------|------|---------|
| 系统控制意图 | 转人工、投诉、退款 | 优先级最高，确定性强 | 规则匹配（毫秒级） |
| 业务意图 | 产品咨询、故障排查 | 需要理解语义 | LLM 分类 |

系统控制意图应该在路由前拦截，不应该被业务分类器处理。

---

## 三、解决方案：前置+后置双层 HITL 架构

### 3.1 架构图

```
用户消息
    ↓
classifier_node
    ├── 前置检测：规则匹配（转人工、投诉、售后）
    │   └── 命中 → 直接返回提示（不调用 LLM）
    └── 未命中 → LLM 意图分类
         ├── greeting → greeting_node → END
         ├── unknown  → unknown_node → END
         ├── product  → product_agent → hitl_checker → END
         ├── fault    → fault_agent → hitl_checker → END
         └── training → training_agent → hitl_checker → END
```

### 3.2 双层检测设计

| 层级 | 位置 | 检测方式 | 覆盖场景 | 优先级 |
|------|------|---------|---------|--------|
| **前置检测** | classifier_node 内部 | 规则匹配 | 转人工、投诉、售后 | 最高（路由前拦截） |
| **后置检测** | hitl_checker_node | 规则匹配 | Agent 拒绝、低置信度 | 兜底（Agent 执行后） |

### 3.3 为什么这样设计？

**为什么前置检测用规则匹配而不是 LLM？**

| 维度 | 规则匹配 | LLM 分类 |
|------|---------|---------|
| 确定性 | 100% 确定 | 有随机性 |
| 速度 | 毫秒级 | 几百毫秒（API 调用） |
| 成本 | 零 | 每次消耗 token |
| 可调试 | 看到关键词就知道为什么命中 | 黑盒 |

系统控制意图（转人工、投诉）是确定性需求，不需要 LLM 的语义理解能力。

**为什么保留后置检测？**

前置检测覆盖了用户主动要求的场景，但 Agent 执行中可能出现的问题（拒绝回答、低置信度、检索失败）仍需后置检测兜底。

## 五、为什么这是面试亮点？

### 5.1 完整的问题解决过程

```
发现 Bug → 分析根因 → 调研方案（参考 GPT 5.5 建议）→ 设计架构 → 实现修复 → 测试验证
```

### 5.2 架构思维

- **系统控制意图 vs 业务意图分离**：不是所有意图都适合 LLM 分类
- **前置+后置双层检测**：高优先级场景前置拦截，低优先级场景后置兜底
- **规则匹配 vs LLM 分类的选型**：根据场景特点选择合适的技术方案

### 5.3 工程实践

- **从单点修复到架构重构**：不是打补丁，而是从根因出发重新设计
- **关键词库设计**：覆盖口语化表达、变体、同义词
- **可扩展性**：新增系统控制意图只需添加关键词，不需要改架构

### 5.4 可以聊的延伸话题

- 如果关键词库覆盖不全怎么办？（LLM 兜底、用户反馈收集）
- 如何评估前置检测的准确率？（测试用例集、bad case 分析）
- 生产环境如何管理关键词？（配置化、热更新）

---

## 六、一句话总结

> 从"转人工被 unknown 吞掉"的 Bug 出发，分析出系统控制意图和业务意图的本质区别，设计了前置规则检测+后置兜底检测的双层 HITL 架构，既解决了当前问题，又为后续扩展奠定了基础。
