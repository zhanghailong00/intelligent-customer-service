# 嵌入式实训箱智能客服系统 — 项目设计文档

## 一、项目背景

### 公司业务
公司制作高校实训道具（嵌入式实验箱），主要客户为高校实验室。

### 业务痛点
- 技术支持团队反复回答相同的故障排查问题
- 高校老师使用设备时遇到问题，无法 24 小时获得帮助
- 培训资料分散，查找不方便

### 项目目标
基于多智能体架构，构建一个智能客服系统，覆盖（产品咨询【待定】）、故障排查（售后）、培训资料三大场景，支持多轮对话和人工介入审核。

### 3.3 LLM 降级策略

```
┌─────────────────────────────────────────────────────────────┐
│                      LLM 降级策略                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户提问                                                    │
│       ↓                                                     │
│  ┌─────────────────┐                                       │
│  │  调用 DeepSeek  │  ← 主模型                             │
│  │  (主模型)       │                                       │
│  └────────┬────────┘                                       │
│           │                                                 │
│      ┌────┴────┐                                           │
│      ↓         ↓                                           │
│   成功       失败                                           │
│      │         │                                           │
│      ↓         ↓                                           │
│   返回结果   ┌─────────────────┐                           │
│              │  调用豆包       │  ← 备用模型               │
│              │  (备用模型)     │                           │
│              └────────┬────────┘                           │
│                       │                                     │
│                  ┌────┴────┐                               │
│                  ↓         ↓                               │
│               成功       失败                               │
│                  │         │                               │
│                  ↓         ↓                               │
│               返回结果   返回错误提示                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**降级策略说明**：

| 场景 | 处理方式 |
|------|----------|
| **DeepSeek 调用成功** | 直接返回结果 |
| **DeepSeek 调用失败** | 自动切换到豆包 |
| **豆包调用成功** | 返回结果 |
| **豆包调用失败** | 返回错误提示："服务暂时不可用，请稍后重试" |


### 3.4 图文混排方案

**核心思路**：
1. 文档切分时 → 保证图片链接不被切断
2. 返回回答时 → 图片链接映射为图片和文字一起返回

**技术选型**：

| 组件 | 选择 | 说明 |
|------|------|------|
| **文档切分** | 按段落切分 | 保证图片链接不被切断 |
| **图片链接格式** | Markdown | `![描述](images/xxx.jpg)` |
| **图片显示** | Gradio | 支持渲染 Markdown 图片 |

**实现步骤**：

| 步骤 | 任务 | 说明 |
|------|------|------|
| **1** | 调整切分策略 | 按段落切分，保证图片链接完整 |
| **2** | 测试返回结果 | 确认回答中包含图片链接 |
| **3** | Gradio 显示 | 确认 Gradio 能渲染图片 |

**切分策略调整**（app/rag/loader.py）：

**优点**：

| 优点 | 说明 |
|------|------|
| **简单** | 不需要修改 metadata，不需要复杂逻辑 |
| **可靠** | 图片链接在切分时就保证完整 |
| **兼容** | Gradio 原生支持 Markdown 图片渲染 |

## 四、技术选型

### 4.1 大语言模型（LLM）

**选择**：DeepSeek API（主模型）+ 豆包（备用模型）

**选型理由**：

| 维度 | DeepSeek | 豆包 |
|------|----------|------|
| **中文效果** | 优秀，适合实训设备领域的专业术语 | 良好，作为备用 |
| **成本** | 低，按 token 计费 | 低，按 token 计费 |
| **响应速度** | 快 | 快 |
| **稳定性** | 高 | 高 |
| **降级策略** | 主模型，调用失败时切换到豆包 | 备用模型，保证服务可用性 |

---

### 4.2 向量数据库

**选择**：ChromaDB

**选型理由**：

| 维度 | 说明 |
|------|------|
| **部署方式** | 纯 Python、嵌入式、零配置 |
| **学习成本** | 低，Python 原生支持 |
| **适用规模** | 中小规模知识库（几百到几千条） |
| **维护成本** | 低，无需额外服务 |

## 五、核心功能设计

### 5.1 智能路由

**功能目标**：根据用户问题类型，自动分配给对应的专业 Agent 处理。

**关键特性**：

| 特性 | 说明 |
|------|------|
| **LLM 意图分类** | 比关键词规则更灵活，能处理模糊表达 |
| **5 种意图** | 产品咨询、故障排查、培训资料、打招呼、未知 |
| **置信度阈值** | 低于 0.5 时降级为 unknown |
| **共享知识库** | 三个 Agent 用同一个 ChromaDB |

**路由流程**：

```
用户提问 → 意图分类（LLM）→ 路由分发 → Agent 处理 → 返回回答
```

---

### 5.2 Agent 集群

**功能目标**：针对不同领域配置专业 Agent，通过角色扮演和专业 Prompt 提升回答质量。

**关键特性**：

| Agent | 角色定位 | 回答风格 |
|-------|---------|---------|
| **产品专家** | 产品知识专家 | 参数、规格、使用说明 |
| **技术支持** | 技术支持工程师 | 诊断步骤、解决方案 |
| **培训顾问** | 培训顾问 | 实验指导、教学大纲 |

**设计决策**：
- 三个 Agent 共享同一个知识库，靠不同 System Prompt 区分角色
- 技术支持 Agent 使用思维链（CoT）推理，提升故障诊断准确性

---

### 5.3 查询重写

**功能目标**：提升检索效果，解决多轮对话中代词和省略主语问题。

**关键特性**：

| 特性 | 说明 |
|------|------|
| **历史对话感知** | 传入最近 3 轮对话历史，理解上下文 |
| **两步检索** | 原始 query + 改写后 query 分别检索，合并去重 |
| **降级机制** | 改写失败时返回原始 query，不影响系统稳定性 |
| **角色感知** | 不同 Agent 有不同的改写上下文 |

**检索流程**：

```
原始 query ─────→ 检索 1 ──┐
                              ├──→ 合并去重 → top_k
改写后 query ───→ 检索 2 ──┘
```

---

### 5.4 HITL 人工转接

**功能目标**：AI 无法处理时自动转人工，确保服务质量。

**关键特性**：

| 检测类型 | 触发条件 |
|----------|----------|
| **Agent 拒绝** | 回复包含"我不确定"、"建议联系技术支持" |
| **用户主动要求** | 用户说"转人工"、"找客服" |
| **置信度低** | 意图分类置信度 < 0.5 |
| **敏感问题** | 涉及退款、投诉等关键词 |

**技术方案**：基于 LangGraph interrupt 机制，支持流程暂停/恢复。

---

### 5.5 多轮对话记忆

**功能目标**：支持多轮对话，记住上下文，实现连续交互。

**关键特性**：

| 特性 | 说明 |
|------|------|
| **LangGraph State** | 使用 State messages 存储对话历史 |
| **上下文传递** | Agent 接收 messages 参数，拼接到 LLM 输入 |
| **截断策略** | 截取最近 10 条消息，避免 token 溢出 |
| **格式兼容** | 兼容 LangChain 消息对象和字典格式 |

**记忆方案**：
- 使用 Gradio history + LangGraph State messages
- Agent 的 run() 方法接收 messages 参数
- 截取最近 10 条消息，避免 token 溢出
- 初期不做 SQLite 持久化，够用

---

### 5.6 知识库管理

**功能目标**：非技术人员能通过 Web 界面更新知识库内容。

**关键特性**：

| 功能 | 说明 |
|------|------|
| **文档上传** | 支持 PDF 格式，自动调用 MinerU API 转换 |
| **文档删除** | 删除 PDF + Markdown + 向量数据 |
| **文档列表** | 显示已导入文档的状态和统计信息 |
| **增量同步** | 自动检测新增、更新、删除的文件 |

---

### 5.7 图文混排

**功能目标**：回答中包含文档图片，提升用户体验。

**关键特性**：

| 特性 | 说明 |
|------|------|
| **按段落切分** | 保证图片链接不被切断 |
| **Markdown 图片链接** | 使用 `![描述](images/xxx.jpg)` 格式 |
| **Gradio 渲染** | Gradio 原生支持 Markdown 图片渲染 |

---

### 5.8 流式输出

**功能目标**：回答逐字显示，提升用户体验。

**关键特性**：

| 特性 | 说明 |
|------|------|
| **伪流式** | LangGraph 同步处理完成后，逐字符显示回答 |
| **打字效果** | 每个字符间隔 0.02 秒，模拟打字效果 |
| **用户感知** | 看到逐字显示，感觉响应更快 |

**当前方案**：伪流式（同步处理后逐字显示）

**后续优化**：真流式（LLM 边生成边返回）
